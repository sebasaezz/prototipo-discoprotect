# Checkpoint H5 · 15 de noviembre de 2026

**Implementado y validado físicamente por el usuario el 15/11/2026.** H5 queda pendiente únicamente de integración a `main`. Se usaron AppAsistente en un Galaxy S22, AppPersonal en un Galaxy S25 y Fastify, SQLite y la web React en un PC Windows. La prueba se realizó en una LAN controlada con perfiles ficticios. [Guion H5](../h5-integration.md)

## Validación física comunicada por el usuario · 27/27

### H5-A · Circuito completo (5/5)

1. El S22 confirmó el SOS y mostró su ID.
2. El S25 mostró el mismo ID.
3. La web del organizador mostró el mismo ID.
4. El incidente persistió al reiniciar Fastify con la misma base SQLite.
5. La cancelación conservó el ID y se reflejó en las tres interfaces.

### H5-B · Interacción y aislamiento (4/4)

1. Soltar antes de 1,5 segundos no creó un SOS.
2. Cancelar el diálogo de confirmación no creó un SOS.
3. Martín envió un SOS con ubicación desconocida y apareció correctamente en las tres interfaces.
4. Antonia y Martín solo vieron sus propias solicitudes. Guardia y organizador consultaron el listado autorizado.

### H5-C · Red, idempotencia y recuperación (8/8)

1. Con Fastify detenido antes del envío, no se confirmó ni se registró un SOS.
2. Dos POST idénticos devolvieron HTTP 201 y 200 con el mismo ID.
3. Guardia y web mostraron un único incidente.
4. Un proxy temporal descartó una respuesta HTTP 201 después de persistir el SOS. El S22 indicó recepción incierta sin ID confirmado.
5. El S25 y la web mostraron el incidente persistido antes del reintento.
6. Reintentar el mismo envío recuperó el mismo ID sin duplicados.
7. Una segunda respuesta descartada volvió a generar un estado incierto.
8. «Consultar servidor» recuperó el incidente persistido sin duplicarlo.

El usuario observó que «Reintentar el mismo envío» no apareció con el proxy apagado. Si falla la comprobación de conexión antes del primer POST, no queda un intento pendiente. Si se pierde la respuesta después del POST, se conserva la clave y el cuerpo para recuperar o reintentar el mismo envío. Las pruebas de recuperación C3 se aprobaron. La observación con el proxy apagado no se reprodujo como fallo de recuperación.

### H5-D · Protección de identidad y sesión (4/4)

1. El cambio de cuenta quedó bloqueado durante el envío.
2. El SOS quedó asociado a Antonia y no apareció en el historial de Martín.
3. Un proxy simuló HTTP 401. AppAsistente invalidó la sesión y ocultó sus datos.
4. Tras el 401, el S22 dejó de emitir una identidad NFC válida.

### H5-E · Regresión NFC final (6/6)

1. Antonia se identificó correctamente con su ficha y sus contactos.
2. Martín se identificó con sus propios datos.
3. Sofía se identificó con sus propios datos.
4. Antonia volvió a identificarse correctamente, incluso con AppAsistente en segundo plano.
5. Cerrar sesión invalidó la identidad NFC.
6. Los incidentes SOS y sus estados permanecieron intactos tras las lecturas NFC.

## Límites y continuidad

- Demostración académica con cuentas y datos ficticios. Carece de certificación como plataforma de emergencias.
- La actualización de incidentes es manual. AppPersonal también consulta al volver a primer plano con **Incidentes** abierto.
- La asignación y resolución por guardias corresponden a H6. El triaje por IA corresponde a H7.
- Los intentos SOS inciertos solo viven en memoria. Tras la muerte del proceso, el usuario debe consultar el historial persistido antes de reenviar.
- Las apps Android usan HTTP sin TLS solo en debug y en LAN controlada. El proxy de desarrollo de Vite escucha en loopback.
- Se simuló el HTTP 401. La prueba no observó el vencimiento natural de ocho horas. Los proxies temporales usados para simular fallos quedaron fuera del producto.
